旧版 `sheetnest` 入口的复杂度估算为：

```text
轮廓类型数² × 最大轮廓点数²
= 81² × 1980²
= 25,721,744,400
```

因此这个数字不是 QT 展开后的 1,005 个副本，也不能归因于某一张图单独生成了 25,721,744,400 个点。它表示 84 张基础图中约 81 种不同轮廓的组合工作量；QT 只在得到位置后映射为 `id#qt-N`。

在仓库根目录执行：

```powershell

cargo test --manifest-path src-tauri/Cargo.toml --lib `
  real_nesting_job_test::real_ds_and_backup_jobs --no-default-features -- `
  --ignored --nocapture
```

测试会读取真实 SVG 路径，不会修改 `printflow-data`。测试输出会列出基础图片数量、QT 总量、每个 SVG 的轮廓点数和最终排版指标。`PRINTFLOW_REAL_LIMIT=16` 可先执行前 16 张做快速回归。

## 预期行为

1. 单个轮廓的复杂度超过单图预算时，只把该 SVG 的所有 QT 实例加入 `unplaced`，并在 `excluded_items` 中返回它的基础 ID 和“轮廓复杂度/点数超过预算”原因。
2. 混合批次达到组合预算时，应按轮廓组分批调用 `sheetnest`；批次之间合并板材结果，不能因为一组复杂轮廓让整批 84 张图片没有结果。
3. 右侧资产列表根据 `excludedItems[].id` 显示红色背景，并保留具体原因；组合复杂度告警还会标记最大轮廓的图片，明确注明“已分批计算，图片仍会继续参与拼版”，避免把复杂度提醒误认为剔除。
4. 复杂度预算属于保护 NFP/GA 内存的候选分组预算，不是墙钟超时。排版 worker 不应因为 35 秒或其它固定时间阈值停止；若算法仍在运行，进度层应持续显示当前阶段。

## 同批测试发现的边界问题

第一个真实 SVG 的物理尺寸为 `40.290 × 44.164 mm`，切割轮廓包围盒约为 `39.539 × 42.643 mm`。原生库会简化轮廓，而画布还需要保留原始图片的完整物理尺寸。直接用轮廓边界放置，再对图片逐个钳制，会产生越界误判或改变间距。

适配层保留原始图片宽高，在求解时补偿图片边缘空白和原生轮廓简化误差；结果只允许整板平移校正，不逐个挪动图片。真实回归必须断言有放置结果、QT 完整、没有越界、没有重叠且满足 3 mm 间距，不能仅打印错误然后让测试通过。

被剔除的是 3 张存在自交的 SVG：`-3`、`-25`、`-50`，合计 26 个测试副本。`-63`（最大轮廓，1,980 点）成功参与了拼版。整批估算仍为 `25,721,744,400`，但已经变成分批提示，不再中断整个请求。

测试还覆盖“大留白 SVG 与普通图片混排”和“图片外框恰好等于板材”的情况：混批没有放下的轮廓会单独重试，避免同批安全余量影响正常图片；重试仍校验完整图片边界，并保持 QT ID 唯一。

本次解决复杂度中断和单图隔离。分批结果还没有跨批余料补排，因此不能把 83 张板材称为最优解；这组数据的利用率仍有优化空间。这里的碰撞检查针对后端求解轮廓，不等同于 Konva 原图显示的完整验收。原生纵坐标约定与原 SVG 留白原点仍需单独对齐验证。
