# 拼版计算完成后的画布内存

## 问题与证据

2026-10-22：拼版计算完成后，WebView 出现 `Out of Memory`。

已复现的资源放大路径：

- 计算完成后，页面用 `Promise.all` 载入全部已放置图片的原始 SVG/base64，包括 SVG 内嵌的打印分辨率图片。
- 图片缓存仅在 `onload` 后写入。同一源图片的 200 个 QT 同时挂载时，实际创建了 200 个 `Image` 加载实例。
- 旧图片缓存位于模块全局，没有容量上限，退出拼版页面后仍保留图片。

这里的 Image 实例数不等于浏览器实际分配的独立位图数；浏览器可能共享内部资源。测试锁定的是重复实例和请求，而不是声称内存下降了 200 倍。

## 当前实现

- 画布仅接收文件路径，不接收全部原始 SVG。
- 仅可见板材请求预览；每个画布实例拥有自己的 `ImpositionCanvasImages`。
- 相同路径与预览尺寸共享排队任务、进行中的加载和最终图片；QT 保留独立位置、旋转和数量。
- 预览请求和解码串行。原生端与右侧缩略图共用渲染锁，避免同时解析多个大 SVG。
- 根据屏幕显示大小选择 128 / 256 / 512 像素预览，原生端也强制最长边不超过 512 像素。
- 已离开屏幕、尚未开始的任务直接移除；进行中的请求返回后检查是否仍有订阅者。
- 未使用的缓存最多 32 张，并按估算的像素及 URL 大小限制为 16 MiB。可见图片另行占用内存，这个限制不是整个 WebView 的内存上限。
- 页面退出时清空图片引用、事件回调和 `src`。组件开发模式的清理与重新挂载也经过检查。
- 单个预览失败不阻塞后续图片。PDF 管理继续按需读取原始 SVG，预览位图不进入导出。

相关实现：`src/modules/imposition/impositionCanvasImages.ts`、`ImpositionKonvaCanvas.tsx`、`ImpositionPage.tsx`，以及原生端 `batch_thumbnails.rs`、`production_imposition.rs`。

TypeScript 构建检查和 `cargo check --lib` 通过。原生端 3 项检查通过，验证尺寸上限、宽高比例、原文件不变，以及真实 SVG 预览。

真实 ds 测试仅读取本地 84 张 SVG，不重新计算或修改任务。使用生产预览函数逐张转换为最长边 256 像素的 PNG：

| 项目 | 实测 |
| --- | ---: |
| SVG 文件数量 | 84 |
| 原文件合计 | 132,523,571 字节 |
| PNG 预览合计 | 3,369,446 字节 |
| 全部转换耗时 | 18.838 秒 |

以上 PNG 大小不包含 base64 编码开销，也不是进程峰值内存。正常画布只加载可见部分，无需等待全部 84 张。
