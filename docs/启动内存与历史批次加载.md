# 启动内存与历史批次加载

## 串行启动入口（2026-10-07）

先用 `Ctrl+C` 停止本项目已有的开发服务，再在项目根目录执行 `npm run tauri dev` 或 `npm run dev:desktop`。两者均通过 `scripts/tauri.mjs`，先在 `src-tauri` 目录完成 `cargo build --no-default-features -j 1`，成功后才启动 Tauri CLI 和 Vite，减少 Rust 编译与 Vite 依赖预构建重叠造成的内存峰值。预编译失败时保留错误退出码，不继续启动前端。

分步预编译仅针对不带额外参数的默认桌面 `dev` 命令。帮助、打包以及带自定义目标、特性或其他参数的命令均原样转交 Tauri CLI，避免使用错误配置预编译。直接执行 `npx tauri dev` 也会绕过本项目入口。Tauri 原生启动流程及钩子说明见 [官方配置文档](https://v2.tauri.app/reference/config/#beforedevcommand)。

此入口减少默认开发配置的首次启动峰值，不能增加系统提交内存额度，也不能保证后续热更新时完全没有重叠。已有 Vite 服务仍会占用内存，因此重试前应停止本项目旧开发任务。

后续 `0.1.24` 启动日志再次出现 `memory allocation of 2621440 bytes failed`，原因是当时默认的 `npm run tauri dev` 仍会绕过分步启动。诊断时系统提交内存约占用 90%；停止本项目 Vite 后，同一份代码单独构建成功，约 23 秒。本次将常用命令与 `dev:desktop` 统一到上述入口，版本号保持不变。

本次故障中，Windows 约 16 GB 物理内存，分页文件手动限制为最大 8 GB，诊断时可用提交内存仅约 586 MB。报错中的 `os error 1455` 是系统提交内存不足；同一份 `windows` 依赖经 `rustc --emit=metadata` 读取成功，随后实际项目单任务构建成功（约 29 秒），没有删除编译缓存。若反复出现，应将 Windows 虚拟内存改为系统管理大小，并按系统提示重启，或先保存工作后关闭不需要的大型软件。

## 开发启动的编译内存不足（2026-09-19）

`npm run tauri dev` 在 Rust 编译期间可能报 `E0786`、`failed to mmap file`，并附带“页面文件太小，无法完成操作（os error 1455）”。这表示 Windows 提交内存不足，不能仅根据 `invalid metadata` 判断编译缓存损坏；此时应用尚未启动。

项目已在 `src-tauri/.cargo/config.toml` 设置 `build.jobs = 1`，并在 `Cargo.toml` 的开发配置中设置 `debug = 0`、`incremental = false`，减少同时编译任务、调试信息和增量构建状态的资源开销。代价是没有完整开发调试符号，后续重新编译可能更慢；不改变业务逻辑。首次切换配置需要重编译依赖。

若系统整体内存仍不足，应先保存其他大型软件中的工作，再关闭不需要的软件，或调整 Windows 虚拟内存。不要自动关闭用户软件或删除历史批次数据。开发时只运行一个 `npm run tauri dev`，避免重复构建争抢锁。

本次验证：Vite 与首次依赖重编译同时运行时仍出现内存不足，因此先退出开发服务，在 `src-tauri` 执行 `cargo build --no-default-features`（成功，7 分 31 秒），再执行 `npm run tauri dev`。完整开发启动成功，PrintFlow 窗口有响应，前端返回 HTTP 200，产品配置请求成功缓存 9,366,278 字节。链接器“正在创建库”被 Rust 标成 `linker_messages` 警告，这是链接输出，不是编译失败。项目设置只能降低构建开销，不能保证系统提交内存耗尽时仍可运行。

## 打开大型历史批次时闪退（2026-10-07）

`ds` 批次包含 84 张图片，原始 SVG 合计约 126.38 MB。仅调用旧版 `load_batch`，不渲染图片卡片，就能复现 `app.exe` 以 `0xe0000008` 退出；Windows 同期有虚拟内存不足事件。旧实现把整个批次 hydrate 成一个响应，序列化和 WebView 传输产生额外的大块内存分配。

现在 `load_batch` 仅返回图片清单及批次属性。前端 `batchHistoryService.ts` 顺序调用 `load_batch_asset_svg`，每次接收一张原图的 UTF-8 二进制内容，再进入下一张；全部完成后才打开编辑页。界面显示加载进度，同一时间仅允许打开一个历史批次。读取失败会显示具体图片错误，不让不完整批次进入编辑状态。

原图按保存的字节读取，不压缩、不改尺寸；旧版内嵌 SVG 记录仍可读取。原生接口只根据批次 ID 和图片 ID 定位保存的资源，不接受前端传入任意文件路径。此修改无需迁移或重写历史记录。

返回历史列表时，临时资源清理也只传图片元数据和文件路径，避免再把整批 SVG 上传回 Rust。已用真实 `ds` 批次验证：84 张原图的 SHA-256 均与磁盘一致，连续打开、返回、再次打开成功，首末图片可显示，数据库记录未改变；打开耗时约 3.7 秒和 4.2 秒。

## 问题

历史批次的数据库只保存 SVG 的持久化路径，但旧的 `list_batches` 在启动时调用 `hydrate_asset`，会把最近 20 个批次的全部 SVG 从磁盘读入内存。大批次会让 `printflow.sqlite` 对应的资源总量远大于单个批次，最终触发 Windows 的大块内存分配失败。

## 处理方式

- `list_batches` 只读取批次记录和轻量资产元数据，保留 `storagePath`，不读取 SVG 文件。
- `load_batch` 读取批次清单，`load_batch_asset_svg` 逐张读取原图，避免将整批 SVG 放进同一个响应。
- 产品配置接口使用流式 `IgnoredAny` 校验，不构造完整 Rust `serde_json::Value`；加载命令返回原始 JSON 字符串，由前端只解析一次。
- 启动配置请求使用单飞 Promise，React 开发模式的双挂载不会重复下载和解析配置。

## 验证

- 本机历史数据库：`printflow.sqlite` 约 1.47GB，assets payload 约 1.25GB。
- 修改后真实启动完成产品配置请求，没有再出现 `memory allocation ... failed`。
- `cargo check --no-default-features -j 1` 通过。
- Rust 单元测试：28 通过，2 个忽略。
- 前端测试：103 通过；`npm run build` 通过。
